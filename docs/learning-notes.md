# 이번 과제의 학습 정리

아래 내용은 이번 구현을 기준으로 작성한 학습 정리 초안이다. 제출 전에 실제로 코드를 실행하고 이해한 내용에 맞게 자신의 표현과 경험을 덧붙인다.

## 1. 게시글 생성 요청은 어떤 순서로 처리되는가?

1. 클라이언트가 `POST /posts`에 제목과 내용을 JSON으로 보낸다.
2. Spring MVC가 요청을 라우팅하고, Jackson이 JSON을 `PostCreateRequest`로 변환한다.
3. `PostController.create()`가 요청 DTO를 받아 `PostService.create()`를 호출한다.
4. Service가 제목·내용의 누락, 공백, 길이를 검사한다. 유효하면 `new Post(title, content)`로 Entity를 만든다.
5. `PostRepository.save()`가 JPA에 저장을 요청한다. Hibernate가 SQL을 실행하여 H2 DB에 저장하고, DB가 생성한 ID가 Entity에 반영된다.
6. Service가 Entity를 `PostResponse`로 변환한다. 트랜잭션이 정상적으로 커밋된 뒤 Controller가 `201 Created`와 `Location: /posts/{id}`를 반환한다.
7. Jackson이 응답 DTO를 JSON으로 변환한다.

Controller는 요청과 응답을, Service는 규칙과 작업 단위를, Repository는 DB 접근을 담당한다는 흐름을 확인할 수 있었다.

## 2. Entity와 DTO를 분리한 이유

Entity는 DB에 저장할 상태와 연관관계를 표현하고, DTO는 API에서 주고받을 데이터를 표현한다. 두 목적이 다르기 때문에 같은 클래스를 쓰면 DB 구조가 API에 그대로 노출된다.

이번 Post에는 `author`와 `createdAt`도 있지만, 응답은 과제에서 요구한 `id`, `title`, `content`만 포함한다. Entity를 직접 반환하면 작성자 정보가 의도치 않게 노출되거나, 지연 로딩과 연관관계 직렬화 문제가 생길 수 있다. `PostResponse`로 변환하면 외부에 공개할 값을 명시할 수 있다.

생성 DTO에는 클라이언트가 입력하는 제목과 내용만 둔다. 수정 DTO는 일부 필드만 받을 수 있고, 응답 DTO에는 서버가 생성한 ID가 필요하다. 생성·수정·응답을 분리하면 서로 다른 규칙을 한 클래스에 섞지 않아도 된다.

## 3. Controller, Service, Repository를 나눈 이유

| 계층 | 이번 코드에서의 책임 | 나누었을 때의 효과 |
| --- | --- | --- |
| Controller | HTTP 경로, 본문 수신, 성공 상태 코드 | HTTP 응답 방식을 바꾸기 쉽다. |
| Service | 게시글 조회, 입력 검증, 부분 수정 규칙, 트랜잭션 | 같은 규칙을 다른 진입점에서도 재사용할 수 있다. |
| Repository | 게시글 저장·조회·삭제 | DB 접근을 한 곳에 모으고 비즈니스 규칙과 분리한다. |

Controller에 모든 코드를 넣으면 HTTP 처리와 DB 변경이 섞인다. 계층을 나누면 요구사항이 바뀌었을 때 어느 책임을 고쳐야 하는지가 분명해진다. 생성자 주입은 필수 의존관계를 생성 시점에 드러내고, `final` 필드로 참조가 바뀌지 않도록 한다.

## 4. PATCH에서는 생략과 null이 다르다

`{"title":"새 제목"}`은 내용 변경을 요청하지 않았으므로 기존 내용을 유지해야 한다. 반면 `{"title":null}`은 수정 필드에 잘못된 값을 명시한 것이므로 `400`을 반환해야 한다.

단순히 제목 필드가 `null`인지 검사하면 JSON에 키가 없었던 경우와 명시적으로 `null`을 보낸 경우를 구별할 수 없다. `PostUpdateRequest`에서 Jackson setter가 호출되었는지를 별도 boolean 값으로 기록하여 두 경우를 구분했다. 제목·내용 중 하나도 전달되지 않은 `{}`도 별도로 거절한다.

모든 입력이 유효한지 확인한 뒤에만 Entity를 변경한다. 제목은 유효하지만 내용은 `null`인 요청에서도 제목이 부분적으로 저장되지 않도록 했다.

## 5. 수정 시 save()를 다시 호출하지 않은 이유

`@Transactional` 안에서 Repository로 조회한 Entity는 영속성 컨텍스트가 관리한다. 조회 후 제목이나 내용을 바꾸면 JPA가 트랜잭션 종료 시 변경을 감지하여 UPDATE를 실행한다. 이것이 변경 감지, 즉 dirty checking이다.

따라서 이번 수정 메서드는 Entity의 상태만 바꾸고 응답 DTO를 만든다. 메서드의 트랜잭션이 커밋된 뒤 별도의 DB 조회에서도 변경된 값이 읽히는지를 테스트했다. 읽기 메서드는 `readOnly = true`, 생성·수정·삭제는 쓰기 트랜잭션으로 구분했다.

## 6. H2를 사용해도 저장 방식에 따라 데이터 유지가 다르다

H2는 DB 제품 이름이고, 항상 메모리에만 저장하는 것은 아니다. `jdbc:h2:mem:...`은 프로세스 종료 시 데이터가 사라지고, `jdbc:h2:file:...`은 파일에 저장한다.

이번 과제는 재시작 후에도 게시글을 조회해야 하므로 파일 DB를 사용했다. 파일 DB라도 `ddl-auto: create`로 실행하면 시작할 때 테이블을 다시 만들 수 있으므로 `update`를 사용했다. 파일 위치와 스키마 생성 정책을 함께 확인해야 데이터가 유지된다. `update`는 이번 학습용 설정이며, 명시적인 DB 마이그레이션을 대신하는 보편적인 운영 전략은 아니다.

## 7. 성공 응답뿐 아니라 실패 응답도 API의 일부다

생성은 `201`, 조회·수정은 `200`, 삭제는 본문 없는 `204`로 구분했다. 입력이 잘못되면 `400`, 게시글이 없으면 `404`를 반환한다. 오류 본문을 `{"message":"실패 이유"}`로 통일하면 클라이언트가 원인을 확인하기 쉽다.

없는 게시글을 삭제할 때도 먼저 조회하도록 구현했다. 이렇게 해야 단순히 삭제 명령만 실행하고 성공으로 끝나는 대신, 요구사항에 맞게 `404`를 반환할 수 있다.

## 8. 검증하면서 확인할 부분

- 제목만 수정했을 때 기존 내용이 남는가?
- 내용만 수정했을 때 기존 제목이 남는가?
- 필드를 생략한 것과 `null`을 보낸 것이 구분되는가?
- 제목 100자·내용 500자는 허용되고 101자·501자는 거절되는가?
- 잘못된 수정 요청 뒤 DB 값이 그대로 남아 있는가?
- 삭제 응답 본문이 비어 있고, 이후 조회는 `404`인가?
- 서버를 재시작한 뒤에도 생성·수정 결과가 남아 있는가?
